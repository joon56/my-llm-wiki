## 한 줄 요약

같은 저장소에서 코드를 고치는 작업 세션과 별도로 **읽기만 하는 질문 세션**을 두고, 첫 프롬프트에 금지 목록·답 형식·인계 형식을 고정한다 — 결정을 위한 긴 문답이 작업 세션의 컨텍스트를 어지럽히지 않고, 정리된 결정만 작업 세션으로 넘어간다.

## 내용

- 금지 목록을 첫 프롬프트에: 파일 수정·커밋·push·저장소 안 코드 작성 금지, 실제 데이터로 가설 판정 금지, 민감 값(좌표, 기기 ID) 출력 금지. 먼저 읽을 문서 4개와 질문 유형별 추가 문서도 지정한다. 데이터를 봐야 하면 저장소 밖 일회용 스크립트를 `python -I`로 돌린다.
- 답 형식을 고정한다: "문서에 있는 사실 / 데이터로 계산한 값 / 의견"을 나누고 근거를 파일·절(예: `SPEC §5.2`, `D-30`)로 단다. 선택지가 있으면 추천 하나와 이유를 주고 결정은 사용자가 한다. 결과를 보기 전에 확정한 정의는 바꾸자고 하지 않고 영향과 선택지만 설명한다.
- 층위를 나누면 문서의 빈칸이 드러난다: "이 단계를 왜 하는지는 문서에 없다", "이 조건의 이유는 문서에 없고 내 해석이다" 같은 답이 나와, 모델의 의견이 사실로 둔갑하지 않는다.
- 인계 형식: "정리해 줘"라고 하면 작업 세션에 붙여 넣을 블록을 낸다 — (1) 정한 것(결정 번호와 답) (2) 새 질문·할 일 (3) 결정 기록·사실 문서로 옮길 후보. 모르는 값은 빈칸(`___`)으로 남겨 사용자가 채우게 해서, 질문 세션이 값을 지어내지 않는다.
- 경계는 실제로 지켜졌다: 사용자가 "작업 들어가자"라고 하자 질문 세션은 작업 대신 정리문을 내주고 작업 세션으로 돌려보냈다. 범위 밖 파일 확인도 "값은 띄우지 않고 머리줄과 행 수만 보겠다"며 먼저 허락을 구했다.
- 인계는 대상별로: 일이 여러 곳에 걸치면 작업 세션(코드·문서)용과 다른 앱(팀 문서 편집)용 인계문을 따로 쓰고, 사용자가 직접 할 일만 목록으로 남긴다.
- 같은 패턴의 현장판: 작업 세션이 판정 기준·파일 흐름·"현장에서 말하지 말 것" 목록을 `.handoff/` 문서로 써 두고, 현장 점검 전용 세션은 그 문서를 읽고 그대로 따랐다. 컨텍스트가 압축된 뒤에도 요약에 규칙이 그대로 남아 점검이 이어졌다.
