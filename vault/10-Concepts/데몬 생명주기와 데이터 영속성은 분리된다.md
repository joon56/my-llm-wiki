## 한 줄 요약

데몬 기반 도구에서 프로세스 상태와 데이터 상태는 별개의 축이다 — `stop`은 프로세스만 죽이고 디스크의 데이터는 그대로 남으며, 상태 조회 명령은 아무것도 바꾸지 않는다.

## 내용

- agentmemory의 `stop`은 백그라운드 프로세스만 종료함. 저장된 기억은 `~/.agentmemory/`에 디스크로 남아 있어서, 다시 시작하면 전부 그대로 복구됨.
- `status`는 순수 조회 명령 — 데몬이 죽어 있어도 절대 대신 띄워주지 않음. "확인 명령이 상태를 바꾸지 않는가"를 도구마다 검증할 것.
- 백그라운드 데몬은 명시적으로 죽이지 않는 한 재부팅 전까지 계속 살아 있음 — "세션이 끝나면 알아서 꺼지겠지"는 틀린 가정.
- 일반화된 멘탈 모델: 데몬 도구를 다룰 때는 항상 두 질문을 분리해서 던진다 — (1) 프로세스가 떠 있는가? (2) 데이터가 어디에 남는가?
- 실용적 귀결: 데이터를 지우고 싶으면 `stop`이 아니라 데이터 디렉토리/삭제 API를 써야 하고, 반대로 잠깐 리소스만 아끼고 싶으면 `stop`만으로 충분함(데이터 유실 없음).
- 세 번째 축은 표준 입출력 상속이다. 데몬을 처음 띄우는 CLI(agent-browser 등)의 출력을 `| tail`로 받으면 데몬이 stdout을 물려받아 파이프가 닫히지 않고 명령이 멈춘다. 첫 실행은 `> /dev/null 2>&1 < /dev/null`로 분리하고 세션 이름(`AGENT_BROWSER_SESSION`)을 고정한다.
- 정리할 때는 '돌고 있는 것'을 셋으로 나눈다: ① 실제 자원을 쓰는 프로세스(에뮬레이터·qemu — `adb emu kill` 후 남은 것은 강제 종료) ② 다음 빌드를 빠르게 하려고 대기 중인 유휴 데몬(Gradle·Kotlin 컴파일 데몬·adb 서버 — `gradlew --stop`, `adb kill-server`) ③ IDE가 소유한 프로세스(언어 서버 — 죽여도 IDE가 되살리니 둔다). java 프로세스가 어느 쪽인지는 `Get-CimInstance Win32_Process`의 CommandLine으로 가른다.
- 종료가 데이터를 만드는 경우도 있다: 에뮬레이터는 끌 때 quickboot 스냅샷을 자동 저장해 GB 단위(워치 AVD만 2.0GB)로 디스크를 다시 쓴다. 막으려면 `-no-snapshot-save`로 띄우거나 config.ini에서 quickboot를 끈다(대신 콜드부트가 20~30초 느려진다).
