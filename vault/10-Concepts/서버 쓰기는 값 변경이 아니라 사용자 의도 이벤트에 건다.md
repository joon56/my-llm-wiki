## 한 줄 요약

UI 이벤트는 사용자 의도와 1:1이 아니다 — 화면 회전의 상태 복원은 사용자 입력 없이 '값 변경'을 일으키고, Enter 한 번은 제출 두 번이 될 수 있다. **서버에 쓰는 부수효과는 클릭 같은 의도 이벤트에만 걸고, 재진입 가드로 한 번만 실행되게 한다.**

## 내용

- 사고 1 — 회전 한 번에 모든 업무가 '완료'로 저장됐다: 목록을 같은 항목 레이아웃의 반복 inflate로 그려 모든 체크박스가 같은 view id를 가졌다. 회전 때 시스템이 id를 키로 상태를 복원하며 한 항목의 체크 상태를 전 항목에 넣었고, `setOnCheckedChangeListener`가 이 복원에도 불려 서버에 '완료'를 썼다.
- 수정: 서버 쓰기를 `setOnClickListener`(사용자 클릭)로 옮기고, 데이터로 다시 그리는 목록 항목은 `isSaveFromParentEnabled = false`로 상태 복원에서 뺐다. 홈·목록·상세에서 가로↔세로를 3회씩(총 9회) 돌린 뒤 서버 통계가 그대로인지 확인했고, '값 변경 리스너가 서버에 쓰는' 곳을 전 화면에서 찾아 없앴다.
- 사고 2 — Enter 한 번에 가입 요청이 두 번 나갔다: 비밀번호 칸의 키 리스너가 ENTER의 ACTION_UP에서만 제출하고 ACTION_DOWN은 소비하지 않았다(false 반환). 흘러간 DOWN이 키보드의 '완료' 동작으로 한 번 더 제출해 같은 이메일 계정이 동시에 2개 생겼다.
- 증상은 원인에서 멀리 나타났다: 겉으로는 "서버에서 바꾼 이름이 앱에 안 보인다"였다. 서버 쪽 계정 목록(`firebase auth:export`)에서 계정 2개를 보고서야 앱은 A를, 수정은 B를 보고 있었음을 알았다.
- 수정: DOWN·UP을 모두 소비하고, 요청 중 재제출을 막는 `submitting` 플래그를 로딩 표시·버튼 비활성화와 같은 지점에서 켜고 끈다.
- 일반화: '값이 바뀜' 이벤트는 상태 복원·데이터 바인딩·초기값 설정 같은 프로그램 변경에도 발생한다. 물리 입력 한 번은 여러 이벤트(DOWN/UP, IME 액션, 빠른 이중 탭)로 쪼개질 수 있다.
- 규칙: 서버 쓰기는 의도 이벤트에 걸고, 재진입 가드로 한 번을 보장하고, 초기값은 리스너를 붙이기 전에 넣는다. 회귀 시나리오에는 회전·화면 복귀·빠른 이중 입력을 넣는다.
