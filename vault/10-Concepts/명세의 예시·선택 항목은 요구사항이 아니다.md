## 한 줄 요약

LLM 에이전트는 명세·인계서의 "예:"·"선택" 항목과 거의 일어나지 않는 오류에 대한 방어까지 전부 구현해 코드를 불린다 — **핵심만 남긴 최소판과 출력 해시를 비교해 군더더기를 계량하고, 평가 항목으로 근거를 대지 못하는 기능은 뺀다.**

## 내용

- 사례: 알고리즘 본체는 코드 297줄(그중 표가 106줄)인데 구현 파일은 2,678줄이었다. 화면 옵션 4종, 키 인자, 출력 대상 주입 계층, 64 KiB 스트리밍, 천 단위 구분 출력, 실행 환경(Windows)에서 쓰이지 않는 Linux·macOS 분기 — 대부분 인계서의 "예:"·"선택" 항목이었다. 사용자가 "왜 이렇게 길어?"라고 두 번 교정했다.
- 진단법: 핵심과 최소 입출력만 붙인 최소판(455줄)을 임시 폴더에 만들고, 같은 입력에 대한 결과 파일 해시와 입력 세트 14개의 결과를 비교했다. 같으면 나머지 약 880줄이 결과와 무관하다는 것이 증명된다.
- 남길 기능은 평가 항목별 표(실행·명세 일치, 구성요소, 용량·속도, 테스트 커버리지, 설계 원칙)로 근거를 대서 정한다. 결과: 구현 2,678→997줄, 실행 파일 41,984→22,528 B, 결과 해시·커버리지·돌연변이 검출은 그대로였다.
- 줄 수 항목이 없어도 길이는 비용이다: 읽는 사람이 핵심을 찾기 어려워지고 용량 평가에도 불리하다.
- 테스트 전용 훅도 구현을 불린다: 오류 주입 매크로를 구현에서 빼고, 테스트 .c가 표준 헤더를 먼저 include한 뒤 `#define malloc(n) test_malloc(n)`식으로 바꿔치기하고 구현 .c를 include한 다음 `#undef`한다. 제출하는 구현에는 테스트 코드가 0줄 남는다.
- 범위 판단이 흔들리면 기준 한 문장을 먼저 선언한다: "빼면 없는 기능이 생기는 것은 넣고, 같은 입력에 같은 결과를 내는 두 번째 방법은 넣지 않는다." 이 기준으로 키 길이 일반화(약 15줄)는 넣고, 같은 복호화를 다른 방식으로 하는 대체 역암호는 뺐다.
- 범위를 묻기 전에 이미 있는 근거 자료(채점 기준표, 과제 문서)부터 연다 — "기준을 알 수 없다"고 했다가 폴더에 기준표가 있다고 사용자에게 교정받았다. 줄 수 예산과 "만들었다 지운 기능" 목록은 다음 작업의 사전 금지 규칙으로 넘긴다.
