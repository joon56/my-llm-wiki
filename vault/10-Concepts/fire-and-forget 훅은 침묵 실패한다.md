## 한 줄 요약

`fetch(url).catch(() => {})` 패턴으로 이벤트를 쏘는 fire-and-forget 훅은 수신자가 죽어 있으면 **모든 이벤트를 소리 없이 버린다** — 세션 0개 기록, 에러 0개 표시.

## 내용

- 실제 사례: agentmemory 훅들이 이벤트를 `fetch(url).catch(() => {})`로 POST하고 있었는데, 데몬이 내려가 있는 동안 모든 이벤트가 조용히 버려졌다. 기록된 세션 0개, 그런데 화면에 뜬 에러도 0개.
- 이때 실제로 쓰인 진단 체인(기록해 둘 가치가 있음): 포트 확인 → MCP는 응답하지만 데이터가 비어 있음 → 훅 소스 코드 읽기 → 해당 프로세스가 연결부(shim)일 뿐임을 발견 → 데몬 시작 로그 확인 → 바이너리 부재 확정.
- fire-and-forget의 트레이드오프: 이벤트 전송이 실패해도 에이전트 작업을 절대 막지 않는다는 장점이 있지만, 그 대가로 실패 신호가 완전히 사라진다.
- 따라서 fire-and-forget 파이프라인에는 **외부 헬스 신호가 반드시 별도로 필요**하다 — 예: 데몬 포트 체크, 주기적인 "최근 N분간 수집 건수 > 0" 확인.
- 일반화: `.catch(() => {})`가 들어간 코드는 "실패해도 괜찮은가"가 아니라 "실패를 어디서 알아챌 것인가"를 먼저 답해야 한다.
- 두 번째 사례는 이 위키의 SessionEnd 아카이브 훅이다. 약 2개월간 멈춰 있었는데 겉으로는 '정제할 새 로그가 없다'는 평온한 모습이었고, 에러 로그도 0건이었다. 앞서 한 번은 최신 아카이브 날짜(7/26)를 오늘과 비교하고서야 끊김을 알아채 수동 변환기로 밀린 세션을 백필했지만, 근본 원인은 2026-11-21에야 찾았다.
- 원인: 훅 명령에 따옴표 없는 Windows 백슬래시 경로를 썼다. Claude Code는 훅을 Git Bash로 실행하는데, bash가 백슬래시를 이스케이프로 먹어 경로가 깨졌고 스크립트가 시작되기도 전에 `command not found`(exit 127)로 끝났다. 그래서 스크립트가 남기게 해 둔 에러 로그도 한 줄 없었다 — 로그 0건은 '정상'이 아니라 '실행 전 단계의 실패'일 수 있다([[Windows에서 bash를 거치는 경로·스크립트는 조용히 변형된다]]).
- 헬스 신호: 정기 실행(주간 정제 등)의 첫 단계에서 가장 최근 산출물 날짜(최신 아카이브 날짜)를 오늘과 비교한다. 할 일이 없어 보이는 것 자체가 수집기 고장의 신호일 수 있다. DB 트리거의 비동기 HTTP(`pg_net`으로 메일 API 호출)도 같은 구조라 키 이름이 틀리면 메일만 조용히 안 가므로, 운영 첫 실행에서 시험 행 insert → 상태 변경 → delete를 한 블록으로 돌려 메일 1통이 실제로 오는지 확인했다.
