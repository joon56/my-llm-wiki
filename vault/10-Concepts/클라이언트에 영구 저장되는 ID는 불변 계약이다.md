## 한 줄 요약

사용자 브라우저의 localStorage 북마크, 캘린더 구독의 이벤트 UID처럼 **클라이언트 쪽에 영구 저장되는 값이 엔티티 ID를 키로 쓰는 순간, 그 ID는 배포 후 사실상 바꿀 수 없는 공개 계약**이 된다.

## 내용

- 서버(원본 데이터) 쪽에서 ID 체계를 바꾸면: 사용자의 localStorage 북마크는 존재하지 않는 ID를 가리키게 되고, 캘린더 앱은 UID가 바뀐 이벤트를 "삭제 후 새로 생성"으로 처리해 알림·수정 이력이 날아감.
- 서버 DB 마이그레이션과 달리 **클라이언트에 퍼진 값은 회수·일괄 변환이 불가능** — 각 사용자의 기기에 흩어져 있기 때문.
- 설계 시점 원칙:
  - ID는 내용에서 파생하지 않는다 (제목 기반 slug를 ID로 쓰면 제목 수정 = ID 변경이 됨)
  - 생성 후 불변인 별도 식별자(연번, UUID)를 부여하고, 표시용 이름과 분리
  - "이 값이 사용자 기기에 저장되는가?"를 스키마 변경 전 체크리스트에 포함
- 이미 배포했다면: 옛 ID → 새 ID 매핑 테이블을 영구히 유지하는 것 외에 방법이 없음. 처음부터 안 바꾸는 게 압도적으로 싸다.
