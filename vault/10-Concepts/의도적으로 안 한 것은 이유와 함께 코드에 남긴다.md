## 한 줄 요약

로드맵의 빈칸은 다음 작업자(사람이든 에이전트든)에게 '할 일'로 읽힌다 — **의도적으로 하지 않은 항목은 결정·이유·깨지는 기능을 코드 옆에 남기고**, 개선 요청이 오면 기획서와 코드를 대조하는 감사부터 한다.

## 내용

- 사례: 스마트워치 센서 앱에 "고도화할 수 있는 것 전부 수행 후 배포본 생성"을 요청받았다. 기획서 로드맵과 코드를 대조하니 신호처리 교체, 지표 추가, 검증 모드까지 이미 전부 구현돼 있었다 — 새로 쓴 코드 0줄, 빌드 검증과 배포 패키징만 했다.
- 하나 남은 미적용 항목(센서 배칭)은 의도적 결정이었고 이유가 코드 주석에 있었다: 배칭하면 1–2초 안에 햅틱을 줘야 하는 실시간 감지가 깨지고, 같은 리스너가 로깅과 감지를 겸해 배칭의 이득도 없다. 이 주석이 없었다면 '미구현 항목'으로 보고 적용해 핵심 기능을 깨뜨렸을 것이다.
- 남길 것: (1) 하지 않기로 한 결정 (2) 이유 (3) 적용하면 깨지는 기능. 위치는 해당 코드 옆 주석이나 결정 기록 — 로드맵을 읽지 않은 사람도 코드를 여는 순간 마주치게 한다.
- 감사가 먼저다: "고도화" 요청에 바로 구현을 시작하지 말고 기획 항목별 구현 여부를 표로 대조한다. 끝난 일을 다시 만들거나, 의도적으로 뺀 것을 '빠진 것'으로 채우는 일을 막는다.
- 남은 항목은 막고 있는 자원으로 분류한다: 코드(끝), 실험(검증 세션), 데이터(분류기 학습용 라벨 없음), 하드웨어(별도 센서 장비), 폐기(문헌·API로 반증). "코드로 되는 건 끝났고 남은 건 실험·하드웨어·데이터"라는 정리가 다음 행동을 정한다.
- 검증 환경의 한계도 같은 표에 넣는다: 에뮬레이터에는 실제 센서·GPS가 없어 감지 로직을 검증할 수 없다. 에뮬레이터는 UI 흐름 시연용으로 두고 실기기 테스트를 최우선으로 올린다.
- 배포물도 문서와 대조한다: 설치 가이드가 워치 앱 APK만 언급하고 있어 폰 동반 앱 APK를 배포 zip에 넣고 가이드를 고쳤다.
