## 한 줄 요약

에이전트 메모리, 사용자의 기억, 사용자가 말한 수치는 모두 관측 시점의 가설이다. **환경을 바꾸기 전에 한 줄 실측으로 확인하고, 메모리에는 상태뿐 아니라 그 상태를 어떻게 적용했는지(일회성 / 영구)까지 적는다.**

## 내용

- 사례 1 — 에이전트 메모리: CLI 하나를 설치하며 `npm install --cache D:\…`를 한 번 썼는데, 메모리에는 "npm 캐시도 D:에 둠"으로 기록됐다. 1주 뒤 `npm config get cache`로 실측하니 여전히 C: 기본 경로였고 캐시가 2.25GB 다시 쌓여 있었다. 그제야 `npm config set cache D:\… --location=user`로 영구화했다.
- 사례 2 — 사용자가 말한 수치: "C:가 3GB 남았다"였지만 실측은 0.8GB였다. 이 차이로 계획의 1순위가 'Temp부터 정리'로 바뀌었다 — 작업 도중 C:가 0이 되면 에디터와 에이전트의 쓰기가 실패한다.
- 사례 3 — 사용자의 기억: "C:에 Ollama 모델이 몇 개 있다"를 전수 확인했다. PATH, 실행 프로세스, `OLLAMA_*` 환경변수, 기본 모델 경로 4곳, 레지스트리 설치 목록(유사 도구 포함), 다른 드라이브 4단계 깊이까지 모두 없었고, 기억의 출처로 보이는 몇 달 전 대화 기록까지 찾아 함께 제시했다.
- 원칙 1: 메모리에 환경 사실을 적을 때는 상태와 함께 적용 방식(일회성 플래그 / 영구 설정 / 수동 작업)을 적는다. 일회성 조치는 상태가 아니다.
- 원칙 2: 메모리·사용자 진술을 근거로 환경을 바꾸기 전에 한 줄 실측(`npm config get cache`, `Get-PSDrive`)으로 확인한다. 메모리는 어디를 볼지 알려 줄 뿐이고, 무엇이 참인지는 실측이 정한다.
- 원칙 3: '없음' 보고에는 확인한 위치 목록과 확인하지 못한 범위를 같이 적는다. 이번에는 모델 파일 확장자 전수 검색을 시간 문제로 중단했다는 사실을 밝혀, '없음'을 과장하지 않았다.
