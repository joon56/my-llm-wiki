## 한 줄 요약

"푸시됐으니 git 연결은 정상", "라이브 미반영은 캐시 때문"이라는 두 판단이 모두 틀렸다 — 실제로는 자격 증명 중복이 계정 선택 팝업을 띄웠고 Pages 배포가 큐에 멈춰 있었다. **전송·인증·배포 큐·라이브 반영은 층마다 따로 확인한다.**

## 내용

- 경위: 정적 사이트 데이터를 갱신해 푸시한 뒤, 에이전트가 푸시 결과만 보고 "git 연결 정상", 라이브 미반영은 "배포·캐시 대기"라고 답했다. 사용자가 "계정 알림이 계속 오류"라고 다시 짚은 뒤에야 인증과 배포 상태를 직접 조회했고, 두 판단 모두 틀린 것으로 드러났다.
- 원인 1(인증): Windows 자격 증명 관리자에 같은 계정이 `git:https://<user>@github.com`과 `git:https://github.com` 두 항목으로 저장돼, Git Credential Manager가 인증 때마다 계정 선택을 요구했다(추적 로그 `Multiple accounts available - prompting user to select one`). 푸시 자체는 성공하므로 명령 출력만으로는 보이지 않는다.
- 수정 1: 사용자 승인 후 `cmdkey /delete:"LegacyGeneric:target=git:https://<user>@github.com"`로 중복 항목을 지우고, `GIT_TERMINAL_PROMPT=0`·`GCM_INTERACTIVE=never`로 읽기·푸시를 다시 시험했다. 이 모드는 창을 띄우는 대신 바로 실패하므로 에이전트가 인증 문제를 직접 볼 수 있다.
- 원인 2(배포): 커밋은 원격에 있었지만 Pages 배포가 약 21분째 `queued`였고, GitHub 상태 페이지는 Pages·Actions 모두 정상이었다 — 서비스 전체가 초록불이어도 내 배포 하나는 멈춰 있을 수 있다. `gh run list`의 빈 출력은 '확인 불가'였는데, 거기에 '캐시'라는 원인을 붙인 것이 오진의 출발점이었다.
- 수정 2: 빈 커밋으로 배포를 다시 걸고, 라이브 페이지에 새 날짜 문자열이 뜰 때까지 상한(약 13분)을 둔 백그라운드 폴링으로 확인했다. 반영은 됐지만 재트리거와 큐 해소 중 무엇이 풀었는지는 불명확하고, 다음 회차 배포는 25초에 끝났다.
- 배포 완료 판정: 푸시 exit 0이 아니라 운영 응답에 새 버전 표식(데이터 갱신 날짜, 새 JS 해시, 번들 안의 새 문자열)이 보이는지로 판정한다.
- 원칙: 원인을 모를 땐 그럴듯한 설명 대신 "미확인"이라 말하고 해당 층을 조회한다. 사용자가 보는 증상(팝업)을 내 쪽 성공 신호(exit 0)로 반박하지 않는다.
