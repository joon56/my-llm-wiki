## 한 줄 요약

자동화 파이프라인의 안전장치는 경고 로그로는 아무것도 막지 못한다 — 비밀정보 검사 같은 게이트는 **exit 1로 실패**해서 다음 단계(커밋, 배포)가 물리적으로 진행되지 못하게 해야 하고, 되돌릴 수 없는 단계 앞에는 사람 확인 지점(STOP 게이트)을 명시적으로 설계해야 한다.

## 내용

- 경고의 한계: 자동화는 로그를 읽지 않는다. "⚠️ API 키가 발견되었습니다"를 출력하고 exit 0 하면, 파이프라인은 그대로 커밋·배포까지 완주한다. 사람도 흘러가는 로그 속 경고를 놓친다.
- 올바른 구조: 검사 도구가 심각(HIGH) 발견 시 **비정상 종료(exit 1)** → CI 스텝 실패 → 후속 스텝 자동 중단. 차단이 기본값이고, 통과가 예외 승인이 되는 방향.
- 이 위키의 적용: `secret_scan.py`가 HIGH 시 exit 1 → GitHub Actions 빌드 스텝 실패 → 배포 차단. 등급 분리도 중요 — 확실한 패턴(API 키 형식)만 HIGH로 차단하고, 애매한 패턴(generic `password:`)은 MEDIUM 경고로 남겨 오탐 피로를 방지.
- 확장: 대량 생성·삭제·커밋처럼 되돌리기 어려운 자동화 단계에는 검사와 별개로 **STOP 게이트**(사람 승인 대기)를 설계에 박아둔다. "스크립트가 알아서 다 했어요"가 가장 위험한 보고다.
- 검사 대상은 저장소만이 아니다: 빌드할 때 환경 변수가 번들에 박힐 수 있으므로 배포된 JS 번들도 검사한다.
- FAIL은 멈추되 판정 단계를 둔다. 번들 검사의 FAIL 1건은 supabase-js가 `sb_secret_` 접두사를 비교하는 라이브러리 문자열이었고, 시크릿 스캔 양성 6건이 전부 스캐너 자신의 정규식 문자열이었던 적도 있다(스캐너 파일은 대상에서 따로 다룬다). '실제 키인가, 패턴 문자열인가'를 가린 뒤에만 통과시킨다.
- 공개용 키 경고는 삭제가 아니라 범위 축소로 푼다: GitHub secret scanning이 경고한 Firebase API 키(`AIza…`)는 모든 APK에 들어가는 클라이언트 식별자이고, 데이터 보호는 보안 규칙이 맡는다. 키를 지우는 대신 API 허용 목록을 기본 27개에서 실제 쓰는 4개로 줄였는데(변경 전 설정 백업), 나중에 추가한 기능이 목록에 막혔으니 기능을 더할 때마다 목록도 갱신한다.
