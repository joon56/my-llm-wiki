## 한 줄 요약

다단계 파이프라인에서 '완료 표시' 단계만 빠지면 **상태 필드가 거짓말을 하고 다음 실행이 같은 입력을 다시 처리한다** — 재처리 전에 산출물 쪽에서 입력 ID를 역검색해 실제 처리 여부를 확인하고, 사용자에게 선택을 묻는 건 그다음이다.

## 내용

- 사례: 이 위키의 정제 루틴에서 `status: raw` 원본 15개 중 최근 10개를 정독·분류하고, 새 노트 제목 4개를 사용자에게 고르게 한 뒤에야 중복을 의심했다. 확인해 보니 10개 모두 이전 정제 런에서 이미 개념 노트의 출처로 인용돼 있었고, 원본의 status 갱신과 역링크 기입만 빠져 있었다.
- 진단법: 개념 노트 폴더에서 세션 ID(8자리)를 grep해 "어느 원본이 어느 노트에 인용됐나"를 매핑했다. 인용된 원본은 distilled로 바꾸고 역링크를 달았고, 교훈 없는 원본은 triaged, 범위 밖은 raw로 남겼다. 새 노트는 0개였다.
- 비용: 사용자가 고른 제목 4개는 모두 기존 노트가 이미 다루고 있었다 — 사용자의 결정 한 번과 원본 10개 정독이 헛수고가 됐다.
- 판단은 실행마다 흔들린다: 이전 런이 개념 노트 7개의 출처로 쓴 세션을 이번 런은 처음에 '교훈 없음'으로 분류했다. 기존 산출물 역참조가 재판단보다 먼저다.
- 원인 구조: 산출물 작성(노트)과 장부 갱신(원본 status·역링크)이 별도 단계라, 앞 단계만 끝나고 세션이 끝나면 상태가 틀린 채 남는다. 장부가 git이 추적하지 않는 로컬 아카이브에 있어 이력으로도 확인할 수 없었다.
- 원칙: 상태 플래그는 캐시일 뿐 진실이 아니다. "이미 처리됐나"는 출력 쪽 증거(입력 ID 역검색, 산출 파일 존재)로 판정하고, 완료 표시는 산출물 작성과 같은 단계에서(가능하면 같은 커밋으로) 한다.
- 점검 순서: 후보를 만들기 전에 (1) 입력 ID 역검색 (2) 기존 산출물과의 개념 중복 확인을 먼저 하고, 사용자 확인은 그다음에 받는다.
